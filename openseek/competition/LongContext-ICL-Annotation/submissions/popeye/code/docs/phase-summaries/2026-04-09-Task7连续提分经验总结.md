## 3. 可以复用的稳定提分工作流
1. 先用一个单任务主线把真实增益做出来，而且必须能打成正式包。
2. 主线一旦线上转正，不要立刻重做方法，先把它当 base。
3. 对 changed rows 做分桶，先找最大风险桶，不要全量瞎审。
4. 只对“强负例”做回退:
   必须有双向一致或足够强的审计证据。
5. 对 split 行一定加第二信号:
   不能只信 pairwise。
6. 如果第二信号说明大部分新答案该保留，就不要继续大面积回退。
7. 最后一层只做极窄、高置信、可解释的事实修补包。
8. 每一包都只替换一个任务，尽量只改几十行、几行，甚至个位数行。
9. 每次都锁住已知 gain 行:
   这轮至少持续保护了 `3deb`、`88c5`、`02e748...`。
10. 每一轮都必须留 artifact:
   changed-row summary、audit、build log、online readout 缺一不可。

## 4. 这次最值得记住的判断标准
### 什么样的动作更容易继续提分
- 在当前 best official baseline 上做超窄 patch，而不是回到老 base 重起一条大线。
- 只改有明确证据的 changed rows，不做“感觉上可能更好”的广域清洗。
- 审计信号越独立越好:
  例如 `pairwise` 之后再叠 `direct generation`。
- 单包改动量越小、理由越清楚，越容易线上转化。

### 什么样的动作更容易把分数打回去
- 在还没收敛 changed-row 风险前继续扩方法面。
- 看见 `manual_review` 就继续整批回退。
- 把 fresh rerun diff 当成 package gate 证据。
- 同时改 judge layout、secondary path、example pool、fact patch 多条轴线。
- 不锁定已验证 target gain 行，导致“修一处坏三处”。

## 5. 以后继续提分时建议强制检查的门禁
- 门 1:
  新包必须基于当前 best official baseline 构建。
- 门 2:
  只允许单任务替换，且必须写清 changed-row count。
- 门 3:
  已知 target rescue 行必须全部保留。
- 门 4:
  对高风险 changed rows 至少要有一种独立审计信号。
- 门 5:
  没有明确证据时，宁可不动，不要把 patch 面做大。
- 门 6:
  每轮结束后都要写在线结果 readout 和方法总结，防止重复踩坑。
